# 2026-09-22 조작 중 끊김 후속 수정

대상 로그는 `20260922-152906-806693-intent-real.jsonl`이다. 사용자가 제외한
에피소드 저장·인코딩 분리는 다루지 않았다. 로봇에 연결하거나 실제 동작을 실행하지 않았다.

## 확인과 수정

| 항목 | 확인한 내용 | 이번 변경 |
| --- | --- | --- |
| Quest 송신 재시도 | WebSocket 버퍼가 차서 전송하지 못해도 `lastSentTime`을 갱신해 다음 XR 프레임의 재시도를 억제함 | 성공한 송신만 주기를 갱신. 다음 XR 프레임의 최신 자세로 재시도. 성공한 송신에는 기존 60 Hz 상한 적용 |
| 입력 관측 시각 | PC 시각을 먼저 읽고 로봇 수신 처리 후 Quest 프레임을 복사하면, 그 사이 도착한 프레임이 관측 시각보다 미래일 수 있음 | 로봇 수신 처리와 Quest 프레임 복사 후 관측 시각을 읽고, 그 시각으로 두 입력을 검증. 입력을 복사하는 동안 로봇 피드백이 오래됐으면 기존 stale 보호로 차단 |
| 불필요한 결과 보관 | 런타임이 결과 6,000개를 deque에 쌓지만 읽는 곳이 없음 | 이 메모리 보관만 제거. JSONL 로그와 에피소드 녹화는 유지 |
| IK 시간 예산 | 동일 q의 캐시 반환은 예산 검사를 우회. 첫 평가에서 예산을 소모해도 SLSQP에 진입 | 캐시 반환 전 예산 검사. 첫 평가가 예산을 소모했으면 최적화 시작 없이 이미 평가한 후보 판정 |

IK 예산은 여전히 협력적 검사다. 실행 중인 단일 네이티브 호출, GC, OS 스케줄링
정지를 강제 중단하는 기능이 아니다. 유효한 후보가 없는 경우 실패하고 기존 보호 정지로
이어지는 동작도 유지한다.

## 아직 확정할 수 없는 원인

- Quest stale 6회: 이후 여러 순번의 프레임이 짧은 시간에 수신되는 구간이 있어 전달 지연과
  몰림의 정황이 있다. 기존 로그만으로 Quest 브라우저, 무선 구간, PC 수신 스레드를 구분할
  수 없다. 재시도 버그가 6회의 주원인이라고 확정한 것은 아니다.
- 오른손 77 cm / 27 cm 입력 점프: 양쪽 샘플 모두 emulated 상태였다. 입력의 추정 위치
  급변을 차단한 보호 동작이다. 추적되지 않은 위치를 소프트웨어가 복구할 근거가 없으므로
  자세 점프 제한이나 재그립 요구를 완화하지 않았다.
- IK 200 ms 지연 2회: 왼팔 IK에서 0~1회 반복 중 발생했다. GC 가능성을 보강하는 실험은
  아래와 같지만, 당시 GC 이벤트가 없으므로 원인 확정은 다음 실행 계측이 필요하다.
- `joint_rate_limit`: PC 계획 간격과 로봇 실제 수신 간격의 차이로 거절 가능. 로봇 측 속도
  제한은 변경하지 않았다. PC 송신 시각과 명령 순번을 추가해 계산 지연과 전달 지터를
  비교할 수 있게 했다. 이 거절 자체를 해결했다고 주장하지 않는다.

200 ms 입력/명령 유효 시간, 100 ms 제어 간격 제한, 관절 속도 제한, emulated 모드 설정은
변경하지 않았다. B 복귀 속도와 시작 ramp도 변경하지 않았다.

## GC 오프라인 실험

LeRobotDataset과 MuJoCo를 import한 별도 프로세스에서 로그의 ACTIVE 결과 구조를
복제하고, 숫자 배열을 NumPy 배열로 복원해 6,000개를 보관했다. 각 조건에서 전체 GC를
명시적으로 5회 호출했다. 실기 로그 재생이나 자동 GC 발생 재현은 아니다.

| 조건 | 전체 GC 중앙값 | GC 추적 객체 수 |
| --- | ---: | ---: |
| 결과 보관 전 | 110.5 ms | 517,766 |
| 결과 6,000개 보관 | 140.3 ms | 613,770 |
| 보관 제거 후 | 113.8 ms | 517,771 |

이 실험은 제거한 메모리 보관이 GC 부담을 늘린다는 근거다. 실제 두 번의 200 ms 정지가
GC였다는 직접 증거는 아니며, 보관 제거만으로 모든 지연이 사라진다는 보장도 아니다.

## 다음 실행에서 남는 진단

- `frame.diagnostics.transport`: 브라우저 실제 송신 시각/간격, XR 콜백 간격과 송신 사이
  최대 간격, 송신 사이 XR 프레임 수, 버퍼로 인한 송신 생략 횟수와 대기 시간.
- `frame.transport`: PC 수신 간격, 원본 샘플 간격, 순번 차이, 디코딩 시간. 100 ms 이상
  수신 공백의 누적 횟수와 마지막 공백을 보관해, 연속 수신으로 첫 프레임이 덮여도 추적한다.
  이 100 ms는 진단 기준이며 입력 허용 시간을 바꾸지 않는다.
- `result.gc_events_since_previous_tick`: 완료된 GC의 세대, 실행 스레드, 시작/종료 시각,
  소요 시간. 최대 32개만 보관하고 소비하며 GC 설정/활성 상태는 바꾸지 않는다.
- `result.control_thread_cpu_ms`, `result.posture_ik.<hand>.thread_cpu_s`: 기존 경과 시간과
  비교하는 현재 스레드 CPU 시간. 다른 스레드/프로세스 전체 CPU 시간은 아니다.
- `result.last_command_dispatch`: 마지막 로컬 송신 시도의 세션/순번/모드, 시작/종료 시각,
  로컬 큐 적재 성공 여부. **로봇 수신 ACK가 아니다.** 재시도/휴지 중 반복된 동일 항목은
  새 명령으로 세지 않는다. 기존 `bridge_rejection_detail.command_seq`와 대응한다.

브라우저 콜백 자체가 늦으면 XR 처리 지연, 콜백이 정상인데 busy skip이 증가하면 송신
적체, 브라우저 송신 간격이 정상인데 PC 수신 공백이 크면 전달/PC 수신 지연을 우선 본다.
이 진단만으로 Wi-Fi와 TCP와 OS 스케줄링을 완전히 분리할 수 있는 것은 아니다.

## 검증과 적용

- 저장을 제외한 Python 회귀 테스트 284개 통과(초기 전체 탐색의 해당 282개와 추가 시각
  검증 2개). 추가 수정 후 REAL 105개, 통합/자세 파이프라인 27개,
  피드백/입력 시각/수신/GC 16개를 해당 범위에서 다시 확인했다.
- JavaScript 실제 소스에 브라우저 stub을 주입한 재현 테스트 통과. 동일 테스트의 첫
  재시도 검사는 HEAD 소스에서 실패해 기존 버그를 확인했다. ES2020+ V8 호스트에서 실행했고
  Quest 하드웨어에서 실행한 테스트는 아니다. `tests/quest_client_transport_test.js`는
  Node가 있는 환경에서도 직접 실행 가능하다.
- 초기 전체 탐색 296개 중 291개 성공, 기존 저장 테스트 5개는 읽기 전용
  `/home/vai/.cache/huggingface/datasets`에 캐시 잠금 파일을 만들지 못해 오류가 났다.
  이번 범위 밖 저장 코드의 회귀라고 판정한 것은 아니며 해당 코드는 변경하지 않았다.
- `git diff --check` 통과. 사용자가 변경해 둔 노트북은 편집하지 않았다.

적용하려면 노트북 실행을 종료한 뒤 **커널을 재시작하고 설정부터 순서대로 실행**한다.
새 PC 수신기가 시작된 뒤 **Quest 입력 페이지를 새로고침하고 XR을 다시 시작**한다.
Python 모듈과 브라우저 JavaScript를 둘 다 새로 읽어야 한다. 로봇 worker 변경은 없다.
실기에서 끊김이 해결됐는지와 미확정 원인은 이 상태의 다음 실행 로그로 확인한다.
